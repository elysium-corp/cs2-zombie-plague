# Диагностика отключения при первом входе

Режим нужен для случая, когда сервер пишет `ProcessMessages has taken more than ...`,
`excessive CPU usage` и отключает игрока с `NETWORK_DISCONNECT_OVERFLOW`.
Он измеряет существующие синхронные обработчики и запуск операций БД.
Логика входа, потоки выполнения, очередь операций по SteamID и сетевые лимиты не меняются.

## Включение

1. Установить **полный** `Elysium.Runtime.Release.zip` из сборки этого PR.
   Нужны согласованные Core-плагины, shared `Common.Di` и приватные копии `Common.Database`.
2. Перед запуском процесса CS2 задать `ELYSIUM_CONNECT_DIAGNOSTICS=1`.
   По умолчанию режим выключен. Изменение переменной требует перезапуска процесса.
   В конфигурации логирования должен быть разрешён уровень `Information`.

Для существующего systemd-юнита:

```bash
sudo systemctl edit cs2@1.service
```

Добавить в override:

```ini
[Service]
Environment=ELYSIUM_CONNECT_DIAGNOSTICS=1
```

Затем выполнить:

```bash
sudo systemctl daemon-reload
sudo systemctl restart cs2@1.service
```

Если сервер запускается вручную в tmux, в том же shell перед существующей командой запуска:

```bash
export ELYSIUM_CONNECT_DIAGNOSTICS=1
```

3. Первым зайти на сервер после полного перезапуска. Сохранить серверный лог,
   затем сразу переподключиться и сохранить продолжение. Нужны обе попытки.
   Если переполнение повторяется только при смене карты, дополнительно сохранить этот сценарий.
4. Передать полный фрагмент от начала подключения до повторного успешного входа вместе
   с SHA сборки/ссылкой на CI. Сохранить и строки `[ConnectDiag]`, и соседние сообщения движка.
5. После сбора установить `ELYSIUM_CONNECT_DIAGNOSTICS=0` в том же override и перезапустить
   процесс. Для tmux убрать переменную перед следующим запуском.

## Что записывается

Каждый замер начинается с `[ConnectDiag]`. Выводится одна запись на выход из этапа,
в том числе при раннем возврате или исключении. Записей на каждом тике нет.

| Поле | Значение |
| --- | --- |
| `stage` | Модуль и этап; у операций БД — `db_dispatch` |
| `player_id`, `session_id`, `steam_id` | Связь этапов одного подключения; неизвестные значения — `-1`/`0` |
| `attempt` | Попытка `player_ready`: `0` внутри первого вызова, следующие — из таймера; `-1` для остальных обработчиков |
| `start_tick` | Начало по монотонному `Stopwatch`, для порядка записей внутри одного процесса; это не игровой тик |
| `elapsed_ms` | Время синхронного этапа до начала вывода собственной записи |
| `operation` | Имя операции БД, включая SteamID, уже переданное вызывающим кодом |
| `lock_wait_ms` | Время от начала замера до получения блокировки `DatabaseTaskTracker` |
| `invoke_ms` | Время **самого вызова** `operation()` до возврата `Task` или синхронного исключения |
| `dispatch_ms` | Полный синхронный вызов трекера: ожидание блокировки, запуск и регистрация задачи |
| `task_status_at_return` | Состояние Task при возврате; `threw_synchronously` при исключении, `not_invoked` при остановленном трекере |
| `thread` | Managed thread ID вызывающего потока, а не номер ядра или OS thread ID |

Покрыты все текущие обработчики `player_connect_full`: Admin, Economy, Statistics,
InfoNotify, PlayerService и RoundService ZombiePlague. Дополнительно измеряются
Steam-авторизация Admin/Communication, Localization и CustomKnife; обработчики
`client_connected` Advertisement, CustomHud/Menu и MapRotation; `client_put_in_server`,
`player_spawn`, ожидание готовности игрока и вложенные этапы `preferences`, `humanize`,
`respawn` ZombiePlague. Это обработчики внутри репозитория, не сторонние плагины сервера.
`db_dispatch` записывается для всех операций трекера, включая сохранения, пока режим включён.

## Как интерпретировать

- Большой `invoke_ms` у `Load ...` указывает на работу, которая выполняется синхронно
  до возврата Task. Это может включать подготовку EF-запроса/JIT; само по себе число
  не доказывает, какая внутренняя операция заняла время.
- Большой `lock_wait_ms` при небольшом `invoke_ms` указывает на ожидание трекера.
- Большой `elapsed_ms` у `humanize`, `respawn`, InfoNotify или RoundService с малыми
  замерами БД переводит поиск на соответствующий игровой этап.
- `invoke_ms` **не является** полной длительностью SQL-запроса. Незавершённая задача
  продолжает работу как прежде, её окончания диагностика не ожидает.
- Вложенные замеры включены в родительские: их нельзя суммировать. Вывод вложенного
  лога также попадает во время родителя. Небольшие значения могут содержать шум диагностики.
- `player_ready` из повторных попыток таймера не следует приписывать исходному
  `CNETMsg_SignonState`; сопоставлять нужно с сессией, номером попытки и порядком событий.
- Замеры показывают прошедшее время, включая ожидание и вытеснение потока, а не чистое CPU time.
  Они не охватывают весь native `ProcessMessages`, диспетчер SwiftlyS2 и JIT самого
  обработчика до его первой инструкции. Если движок сообщает секунду, а все этапы
  короткие, нужен профиль native/managed стека вокруг подключения.
- Запись на выходе означает окончание замера, а не успешность обработчика.
  Исключение и его исходный контракт сохраняются; причина ошибки остаётся в обычном логе.

Технические записи не содержат SQL, паролей, токенов, IP или текста чата.
SteamID нужен для сопоставления операций между плагинами; игрокам эти записи не отправляются.
