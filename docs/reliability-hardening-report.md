# Отчёт об исправлении утечек и проблем стабильности

Базовая версия: `origin/develop`, commit `c64c4ec714e551e32ba6d9aa63e0b87495216244`.

Утечкой в этом отчёте называется подтверждённое нарушение владения: код создаёт долгоживущую подписку, таймер, задачу, entity, patch или коллекцию, но не имеет симметричного и ограниченного пути освобождения. Возможные проблемы без достаточных доказательств реальной утечки обозначены как риски.

## Краткий результат

- DI и плагины выполняют rollback при ошибке на любой стадии загрузки;
- подписки, команды, таймеры и entity получили симметричный teardown;
- фоновые операции получают cancellation и ограниченное ожидание при unload;
- файловый I/O SupplyBox вынесен из игрового потока;
- убраны лишние аллокации на часто вызываемых путях;
- растущие коллекции и входные файлы получили верхние ограничения;
- каталог событий содержит параметры контекста, nullable, mutable и признак отменяемости.

## Подробное объяснение исправлений

### 1. Жизненный цикл плагинов и DI

**Что было:** исключение после создания DI-модуля, например в `OnStart`, настройке shared interfaces или `OnReady`, прерывало загрузку до обычного `Unload`. Provider мог остаться в статическом реестре `DependencyManager`.

**Почему это утечка:** статический реестр является GC root. Пока provider находится в нём, GC не может освободить граф сервисов, плагин и связанные объекты. Каждый reload мог добавлять новый граф поверх старого.

**Что исправлено:** каждая стадия выполняется с rollback. Модуль сначала удаляется из реестра, затем уничтожается provider. `Cleanup` идемпотентен, а несколько ошибок очистки объединяются без потери первоначальной причины.

**Доказательство:** для каждой успешной регистрации существует путь удаления, даже если загрузка завершилась исключением до `Unload`; повторный cleanup не освобождает ресурсы дважды.

### 2. Диагностика Common.Hooks

**Что было:** исключения подписчиков подавлялись без диагностики.

**Почему это опасно:** обработчик мог упасть до собственного `Unhook`, а найти конкретную подписку и контекст было невозможно.

**Что исправлено:** `HookService` передаёт исключение в `ILogger` или diagnostic callback и продолжает вызывать остальные подписки.

**Доказательство:** unit-тест проверяет исключение, тип контекста и delegate, а также выполнение следующего обработчика.

### 3. Эффекты игроков

**Что было:** глобальный provider сильно удерживал `ISwiftlyCore`, игроков и эффекты между reload. Таймеры уничтожались неидемпотентно, неудачно запущенный эффект мог попасть в реестр.

**Почему это утечка:** образовывалась цепочка `static -> core -> effect -> player`; пока она существовала, весь граф оставался достижимым для GC.

**Что исправлено:** состояние разделено по экземплярам core через слабое владение; реестр синхронизирован; эффект добавляется только после успешного запуска; дубликаты подавляются; таймер освобождается идемпотентно. На unload вызывается `EffectService.Release(Core)`.

**Доказательство:** статический контейнер больше не содержит сильную ссылку на core, а у каждого зарегистрированного эффекта есть единый завершающий путь.

### 4. Дублирующий контроллер частиц

**Что было:** одновременно существовали две реализации tracer-частиц, включая регистрацию неиспользуемой реализации в DI.

**Почему это опасно:** два владельца одинакового ресурса допускают повторные particle/timer цепочки и делают teardown неоднозначным.

**Что исправлено:** дублирующий `ParticleController`, интерфейс и DI-регистрация удалены. Оставшийся `WeaponController` очищает tracer/grenade state в `Dispose`.

**Доказательство:** в composition root остался один владелец tracer-частиц.

### 5. SupplyBox: entity, звук и таймеры

**Что было:** таймер раунда, отложенная установка модели, sound handles и entity могли пережить окончание раунда или reload.

**Почему это утечка:** scheduler callback удерживал `SupplyBoxEntity`; при повторных раундах старые объекты могли накапливаться.

**Что исправлено:** `SupplyBoxEntity` получил идемпотентный `Dispose`; таймеры отменяются и освобождаются, звук останавливается, entity удаляются. Callback проверяет disposed и поколение раунда. GUID команды сохраняется и удаляется при unload.

**Доказательство:** `StopRound` очищает весь набор коробок и timer появления; после dispose отложенный callback не изменяет и не создаёт entity.

### 6. Конфигурация SupplyBox

**Что было:** JSON читался и записывался синхронно в игровом потоке, файл перезаписывался напрямую, а серия изменений могла создавать устаревшие записи.

**Почему это вызывает фризы:** задержка диска, сериализация и flush блокировали игровой поток. Сбой во время перезаписи оставлял повреждённый JSON.

**Что исправлено:** I/O вынесен в фон и сериализован через `SemaphoreSlim`; используются snapshots, поколение карты и версия данных. Файл сначала пишется в `.tmp`, затем атомарно заменяется. Добавлены лимиты 1 MiB и 512 точек.

**Доказательство:** игровые callbacks больше не выполняют файловый I/O; устаревшая версия не заменяет новую, а старый целый файл сохраняется до успешной подготовки замены.

### 7. Лазерные мины

**Что было:** продолжения `Task.Delay` и `NextTick` захватывали игрока после unload, отклонённая entity уничтожалась не на всех ветках, pending-словарь использовался из нескольких потоков без синхронизации.

**Почему это опасно:** callback мог обратиться к невалидному player/core или создать мину после выгрузки. Гонка могла потерять операцию, которую unload уже не отменит.

**Что исправлено:** добавлены shutdown token, синхронизация pending-операций, проверка token в игровом callback и dispose entity на всех ветках отказа.

**Доказательство:** после cancellation callback не проходит проверку перед `Spawn`, а все операции принадлежат синхронизированному реестру.

### 8. Способность Trap

**Что было:** `UnHook` не освобождал созданную ловушку, repeat-таймер и delayed-despawn callback.

**Почему это утечка:** scheduler продолжал удерживать `TrapEntity`, caster и particle после отвязки роли.

**Что исправлено:** способность уничтожает ловушку при замене и `UnHook`; `TrapEntity.Dispose` идемпотентно удаляет particle и оба таймера.

**Доказательство:** любой ресурс из `TrySpawn` принадлежит способности и имеет прямой путь освобождения.

### 9. Отслеживание гранат

**Что было:** каждый tick копировал словари и списки, количество записей не ограничивалось.

**Почему это вызывает фризы:** частые аллокации повышают частоту GC, а растущий список увеличивает длительность каждого следующего tick.

**Что исправлено:** буферы переиспользуются, удаление выполняется обратным проходом без копии, введены лимиты 64 гранаты на игрока и 512 глобально, состояние очищается в `Dispose`.

**Доказательство:** старые копии коллекций отсутствуют в tick-пути, объём retained state имеет фиксированный максимум.

### 10. Управление раундами

**Что было:** preparation-respawn timers не имели полного teardown, ошибка запуска режима не гарантировала `End`, а некорректные веса могли привести к `Random.Next(0)`.

**Почему это опасно:** callback старого раунда мог выполниться в новом; частично запущенный режим сохранял подписки; исключение останавливало выбор режима.

**Что исправлено:** respawn timers принадлежат `RoundManager` и отменяются; системное завершение раунда нельзя отменить hook-ом; failed start вызывает cleanup один раз; учитываются положительные веса с суммой `long`.

**Доказательство:** engine round-end завершает режим, failed start проходит через `End`, алгоритм не вызывает генератор со значением `0`.

### 11. Statistics, Database и Metrics при остановке

**Что было:** синхронные ожидания фоновых запросов могли длиться неопределённо, часть задач не получала shutdown cancellation.

**Почему это вызывает фриз:** `Unload` синхронен; зависший PostgreSQL или HTTP endpoint мог удерживать игровой поток внутри `Wait`.

**Что исправлено:** начальный refresh статистики неблокирующий; task tracker владеет shutdown token; ожидание при остановке ограничено 2–3 секундами.

**Доказательство:** unload теперь имеет конечную верхнюю границу ожидания. Это ограничивает фриз, но не означает, что сторонний драйвер мгновенно прервёт уже начатый системный вызов.

### 12. Endpoint и буфер Metrics

**Что было:** разрешался произвольный HTTP endpoint, словарь rate-limit keys мог расти, spool часто обрезался около предельного размера.

**Почему это опасно:** внешний HTTP допускает перехват данных; неограниченная cardinality расходует память; частый trim создаёт лишний disk I/O.

**Что исправлено:** по умолчанию разрешён HTTPS; HTTP требует явной настройки и допускается только для loopback. URI с userinfo отклоняется. Warning keys ограничены, trim оставляет запас 10% в пределах 64 KiB–4 MiB.

**Доказательство:** внешний небезопасный HTTP не проходит validation, коллекции имеют верхнюю границу, spool после trim находится ниже порога следующего срабатывания.

### 13. MovementUnlocker patch

**Что было:** unload пытался откатить patch без подтверждения, что этот экземпляр успешно его применил.

**Почему это опасно:** повторная или неудачная загрузка могла откатить чужое состояние или сохранить неправильный флаг владения.

**Что исправлено:** наличие patch проверяется до применения, успешное применение запоминается экземпляром, ownership сбрасывается в `finally` при revert.

**Доказательство:** экземпляр откатывает только собственный patch и очищает флаг даже при исключении платформы.

### 14. Команды, события и queued callbacks

**Что было:** некоторые команды и handlers регистрировались без сохранения ID или обратной операции; поставленный в очередь `NextTick` мог выполниться после unregister.

**Почему это утечка:** registry удерживает delegate, а через него экземпляр плагина. После reload старый и новый обработчики могли работать одновременно.

**Что исправлено:** GUID команд сохраняются и передаются в `UnregisterCommand`; подписки удаляются симметрично; callback проверяет состояние регистрации; cleanup защищён от повторения.

**Доказательство:** у каждого изменённого места регистрации есть обратная операция, queued callback не выполняет игровую работу после unregister.

### 15. Владение таймерами SwiftlyS2 Scheduler

**Что было:** часть cleanup-кода после `Cancel()` вызывала `Dispose()` у `CancellationTokenSource`, возвращённого `RepeatBySeconds` или `DelayBySeconds`.

**Почему это вызывает исключение:** этот token является внутренней частью timer, который всё ещё хранится в очереди SwiftlyS2 до следующего прохода scheduler. `SchedulerManager.ExecuteTimer` обращается к уже уничтоженному token и выбрасывает `ObjectDisposedException`. Особенно вероятно это при завершении эффекта, раунда, ловушки, мины или SupplyBox непосредственно во время обработки timer.

**Что исправлено:** scheduler token только отменяется через `Cancel()`, после чего локальная ссылка очищается. `Dispose()` оставлен только для `CancellationTokenSource`, которые создаёт и полностью контролирует сам плагин, например shutdown и linked tokens фоновых задач.

**Доказательство:** во всех изменённых путях `DelayBySeconds`/`RepeatBySeconds` отсутствует преждевременный `Dispose`; SwiftlyS2 сохраняет владение token до удаления timer из собственной очереди.

### 16. Параметры контекста событий

**Что было:** каталог показывал только имя типа контекста, без параметров, возможности отмены и допустимости изменения.

**Что исправлено:** схема обновлена до v2; добавлены `isCancellable` и `contextParameters` с `name`, `type`, `nullable`, `mutable`.

**Доказательство:** генератор обнаружил 81 событие, 187 параметров и 29 отменяемых событий. Отсутствующий или неоднозначный context завершает CI ошибкой.

## Runtime-проверка

Для окончательного подтверждения на CS2-сервере необходимо выполнить:

1. 50 последовательных reload затронутых плагинов;
2. 100 переходов между раундами;
3. одновременное использование мин, ловушек, гранат и SupplyBox;
4. отключение PostgreSQL и Metrics endpoint во время unload;
5. замеры managed heap после принудительного GC, scheduler callbacks, игровых entity, длительности unload и p99 frame time.

Исправление считается подтверждённым в runtime, если после прогрева отсутствует монотонный рост heap/callback/entity, старые экземпляры не вызываются после reload, unload укладывается в предел 3 секунды, а p99 frame time не ухудшается относительно базового `develop`.
